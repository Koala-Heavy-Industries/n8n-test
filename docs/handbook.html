運用台帳ハンドブック

メンバーのアカウントと権限を、台帳リポジトリに書いてある状態へ自動で合わせ続ける仕組みです。 追加も、役割変更も、削除も、やることは同じ — 台帳を編集する PR を出してマージするだけ。 あとは自動化が実サービスを台帳に追いつかせ、自動化できない作業は担当者にタスクとして依頼し、 終わるまで催促します。

目次

1. 中核の考え方 2. 構成要素 3. メンバーの追加・変更・削除 4. 依頼が来たとき 5. サービス・役割を変える 6. 環境の運用 7. 安全装置とルール 8. いま動く範囲 9. 用語

1. 中核の考え方 — 宣言して、収束させる

「誰に何を付与するか」を人が宣言し、実サービスをそれに合わせ続ける。

この仕組みには「追加処理」も「削除処理」も存在しません。あるのは 台帳に書かれた「あるべき状態」と、実際の付与状況を比べて、差を埋めるという ひとつのループだけです。追加・役割変更・チーム異動・削除は、そのループの現れ方が違うだけです。

desired

台帳(members/)

人が PR で宣言する「あるべき状態」。役割・所属チーム・在籍状況を書く。

→

reconcile

リコンサイラ

差分を計算し、API で実行するか、人へのタスクとして起票する。

→

actual

実サービス + state/

Keycloak などの実際の状態と、その記録。差が無くなれば「収束」。

この形にしたことで、いくつかの性質が自動的に手に入ります。

  • やり残しが定義できる — 「あるべき状態」と「実態」の差が、そのまま未完了の一覧になります。
  • 失敗しても自力で直る — API 呼び出しが失敗しても差が残るので、翌日の定期実行が再試行します。
  • 取り消せる — 誤った変更は PR を revert すれば、逆方向に収束します。
  • 監査証跡が勝手に残る — 誰がいつ何を承認し、いつ付与されたかが Git の履歴そのものです。
覚えておくこと

削除は「削除処理を走らせる」のではなく、台帳に「もういない」と書くだけです。 あるべき権限がゼロになるので、差分が全剥奪になります。

2. 構成要素

2つのリポジトリと、3つのサービス。

khi-ledger(台帳)

データの置き場。ワークフローやコードは入っていません。

  • members/ — 人が PR で編集する「あるべき状態」
  • catalog/ — 対象サービス、役割マトリクス、チームマトリクス
  • state/ — 自動化だけが書く「実態」と未完了タスク

n8n-test(自動化)

仕組みそのもの。設計ドキュメントと実行環境。

  • workflows/ — ワークフロー定義(Git 管理・CLI で反映)
  • docs/design/ — 設計 00〜08
  • compose.yaml / scripts/ — 検証環境と運用スクリプト

動いているサービス

サービス役割入口
n8nワークフローの実行基盤。すべての認証情報を保持するlocalhost:5678
Keycloakプロジェクト IdP。従業員と協力会社メンバーの両方が登録されるlocalhost:8080
Mailpit検証用の受信箱。通知チャネル未決のまま全フローを試せるlocalhost:8025

ワークフローの構成

機能は小さなサブワークフローに分かれていて、互いを呼び出します。 台帳の読み書きは ledger-read / ledger-write に集約されているので、 将来データの置き場を変えても呼び出し側は変わりません。

ワークフロー役目
reconcile差分を計算し、適用する。この仕組みの心臓部
service-keycloakKeycloak を操作するコネクタ。何度呼んでも同じ結果になる
ledger-read / ledger-write台帳の読み書き。競合したら読み直して再試行する
notify通知。チャネル依存はここだけに閉じ込めてある
request-approval承認リンク付きの依頼を送り、応答まで待つ(汎用)
remind-scheduler未完了タスクの催促とエスカレーション、契約期限の監視
task-complete完了リンクの受け口。押されるとタスクを閉じる
cron-daily毎日9時に reconcile → remind-scheduler を実行

3. メンバーの追加・変更・削除

やることは全部同じ — 台帳の YAML を編集する PR を出す。

申請する人メンバーを迎える / 役割を変える / 抜ける
  1. 台帳に PR を出す。 khi-ledger の members/ を編集します。
  2. レビューを受けてマージする。 このマージが承認そのものです。
  3. あとは待つだけ。 自動でできる操作は数分で反映され、人手が要る作業は担当者にタスクが飛びます。

新しく迎えるとき

members/<id>.yaml を新規作成します。<id> はメールアドレスのローカル部です。

name: 山田 太郎
email: taro@example.com
affiliation: employee          # employee か partner:<会社名>
role: developer                # developer / reviewer / pm / admin
teams: [alpha]                 # 兼務するなら [alpha, beta]
status: active
accounts:
  github: taro-yamada

協力会社メンバーの場合は sponsor(受入責任者)と contract_until(契約終了日)が必要です。

役割やチームを変えるとき

role: や teams: を書き換えるだけです。新旧の差分だけが適用されるので、 付け直しは起きません。effective_from: を書けば未来の日付から有効にできます。

抜けるとき

status: left
left_at: 2026-09-30    # この日いっぱいは有効。翌日に停止される

ファイルは消さないでください。 在籍中の権限履歴の証跡として残します。 即時に遮断が必要なインシデント対応では immediate: true を添えます。

マージすると何が起きるか

  • Keycloak — ユーザーが作成され、役割とチームに応じたグループに入ります。削除時はアカウント停止(+セッション失効)とグループ全剥奪。
  • ライセンス・Claude など人手が要るもの — 担当者にタスクが起票され、完了リンク付きの依頼メールが届きます。
  • state/ への記録 — 適用結果が bot によってコミットされます。失敗した分は記録として残り、翌日また試されます。
まだ自動化されていない部分

GitHub の Team 所属は現在まだコネクタが未実装で、実行サマリに「未実装」として表示されます。 黙って無視されることはありませんが、当面は手動で対応してください。

4. 依頼が来たとき

メールのリンクを開くだけで完了報告になります。

タスクの担当者ライセンス購入、アカウント招待など

自動化できない作業は、メールで依頼が届きます。件名は「未完了のお知らせ」、 本文に対象メンバー・手順・期限、そして完了リンクが入っています。

  1. 作業する。 本文の手順に従って購入や招待を行います。
  2. 完了リンクを開く。 それだけで記録されます。ログインも返信も不要です。

リンクを開くとタスクが閉じ、その権限が付与済みとして台帳に記録されます。 これで「あるべき状態」と実態の差が埋まり、以後この依頼は届かなくなります。 誤って二度開いても「既に完了しています」と表示されるだけです。

放置するとどうなるか

  • 3日ごとにリマインドが届きます(最大3回)。
  • 期限を超えて3回催促しても未完了なら、管理者へエスカレーションされます。
  • 必須でないタスク(PC の IP 登録など)は催促は続きますが、エスカレーションはされません。
受入責任者(sponsor)協力会社メンバーの契約管理

担当している協力会社メンバーの契約終了日が近づくと、30日前から確認メールが届きます。 継続するなら contract_until を更新する PR を、終了するなら status: left にする PR を出してください。

重要

契約期限が過ぎてもアクセスは自動では止まりません。 契約更新の事務手続きが遅れただけで業務が止まることを避けるための、意図的な判断です。 そのぶん、期限超過の通知が届いたら必ず対応してください。放置すると アクセスが残り続けます。

5. サービス・役割を変える

対象サービスはコードではなくデータ。増減はカタログの編集だけで済む。

「どのサービスを、どう扱うか」は catalog/ の YAML に書かれています。 サービスが増えても減っても、ワークフローには手を入れません。

連携のしかたは3つの軸で決まる

操作(追加・変更・削除)ごとに、次を指定します。

軸取りうる値意味
実行方式
execute		 api / iac-pr / prepared / manual / idp 誰がどうやって実行するか。API で自動実行するのか、人にタスクを出すのか
確認方式
verify		 api / event / human / none やったことをどう確認するか。実行が手動でも確認だけ自動化できるのが要点
枠
capacity		 総枠・使用数・閾値 シート数の管理。空きが減ったら先回りで調達タスクを起票する

実行と確認を分けているのが効きます。書き込み API が無いサービスでも読み取り API さえあれば、 タスクは人の報告を待たずに自動で閉じられますし、 フローを通さず管理画面で直接行われた変更も検出できます。

よくある変更

やりたいことやること
対象サービスを増やすcatalog/services.yaml に1エントリ追加。自動実行するならコネクタを1本作る
対象サービスを外すenabled: false にする(履歴保持のため行は消さない)
手動運用を自動化に昇格コネクタを作り、execute を api に変える
役割ごとの権限を変えるcatalog/role-matrix.yaml を編集
チームを新設するcatalog/team-matrix.yaml に追加
カタログの変更は影響が広い

1行の編集が全メンバーに波及します。剥奪が一定数を超えるとリコンサイラが自動で停止するので、 大規模な変更を意図して行うときは事前に周知してください。

6. 環境の運用

起動、ワークフローの反映、状態の確認。

起動する

cp .env.example .env          # 秘密値を埋める
docker compose up -d
./scripts/setup-keycloak.py   # realm・グループ・サービスアカウント(何度でも実行可)
./scripts/import-credentials.py
./scripts/deploy-workflows.py

ワークフローを直したら

ワークフローは n8n の画面ではなく workflows/*.json で管理します。 画面で編集すると Git と食い違うので、必ずファイルを直してから反映してください。 

./scripts/deploy-workflows.py   # インポート → 有効化 → 再起動

動きを確かめる

# 台帳と実サービスを今すぐ収束させる
./scripts/run-workflow.py reconcile '{}'

# 台帳の中身を見る
./scripts/run-workflow.py ledger-read '{"kind":"members"}'

送信されたメールはすべて Mailpit で確認できます。 通知チャネル(Gmail / Slack)が未決のままでも、承認・依頼・催促の全フローをここで検証できます。

検証時の注意

待機を含むフロー(承認)や多段のサブワークフロー呼び出しは、CLI 実行では正しく動きません。 稼働中のインスタンスで動かす必要があるため、Webhook トリガーの一時ワークフローから 呼び出して確認します。実運用は定期実行と Webhook 起動なので影響はありません。

いつ何が走るか

タイミング処理
毎日 9:00差分の収束 → 未完了タスクの催促・エスカレーション・契約期限の確認
台帳のマージ時即時の収束(予定。現在は日次のみ)
完了リンクのクリック時タスクを閉じ、権限を記録

7. 安全装置とルール

壊れ方をあらかじめ決めてある。

大量剥奪を止める

1回の実行で剥奪が5件を超えると、何も適用せずに停止します。 マトリクスの編集ミスで全員のアクセスが一斉に消える事故を防ぐためです。 意図した一括処理なら上限を一時的に上げます。

失敗しても止まらない

あるサービスの操作が失敗しても、他のサービスの処理は続きます。 失敗は台帳に記録され、差が残るので翌日また試されます。

権限が残る方向の失敗は監査で拾う

付与の失敗は業務が止まるので気づきます。剥奪の失敗は気づきにくいため、 未収束として一覧に残り続けます。契約期限切れも自動遮断せず、通知で対応を促します。

自動化自身も監視対象

n8n はすべての認証情報を持ち、台帳の承認プロセスを技術的には迂回できます。 n8n の管理者権限は台帳の承認者と同等以上の特権として扱ってください。

守ってほしいルール

  • state/ は手で編集しない。 自動化の管理領域です。実態と食い違うと収束の判断が狂います。
  • ワークフローは画面で編集しない。 Git のファイルを直して反映します。
  • 緊急時は先に止めてよい。 インシデント対応では Keycloak を直接停止して構いません。 ただし24時間以内に台帳へ追随する PR を出してください。出さないと監査で「不明な変更」として報告され続けます。

8. いま動く範囲

実機で確認できているものと、これからのもの。

機能状態補足
メンバーの追加・役割変更・チーム異動・削除動作Keycloak への反映まで通し確認済み
台帳の読み書き動作競合時の再試行を含む
タスク起票・催促・完了リンク動作エスカレーションまで確認済み
通知・承認リンク動作宛先は Mailpit。本番チャネルは未決
大量剥奪の停止動作停止時は実サービス無変更を確認済み
GitHub Team の自動反映未実装サマリに「未実装」と表示される
PC・サーバ・IP の登録未実装NetBox の追加が必要
定期監査・再認定未実装実サービスとの突合、半期の棚卸し
台帳の CI 検証動作スキーマ・制約の検証、state/ の保護、権限差分のプレビュー
ブランチ保護(申請者≠承認者)未設定検証環境の制約で設定できない。本番移行時の必須項目
マージ時の即時反映一部現在は日次のみ。取りこぼしても翌日収束する
本番移行前に必ず

検証環境のリポジトリではブランチ保護が使えないため、 「申請者≠承認者」「force push 禁止」「bot の書き込みを state/ に限定」は まだ規約であって強制ではありません。本番の台帳は保護設定を有効にしてから運用を開始してください。

9. 用語

この資料と設計ドキュメントで使う言葉。

用語意味
台帳権限のあるべき状態と実態を記録した Git リポジトリ(khi-ledger)
収束あるべき状態と実態が一致していること。差があれば未完了
リコンサイラ差分を計算して埋めるワークフロー(reconcile)
grant「このサービスでこの権限」を表す値。例: group:team-alpha
コネクタ個々のサービスを操作するワークフロー。何度呼んでも同じ結果になるよう作る
チームと Team「チーム」は組織上の単位(alpha)。「Team」はそれを GitHub 上で表したもの(alpha-devs)
キルスイッチKeycloak のアカウント停止。SSO 経由のアクセスをまとめて止める手段
fail-open失敗したときにアクセスが残る側に倒れること。どの失敗がそうなるかは設計書 08 に一覧がある

詳細な設計判断とその理由は、n8n-test リポジトリの docs/design/ にあります (00 全体像 / 01 メンバーライフサイクル / 03 カタログと台帳 / 04 通知と承認 / 05 実行環境 / 06 GitHub 連携 / 08 統制と安全装置)。 この資料は実装済みの範囲を運用者向けにまとめたものです。
